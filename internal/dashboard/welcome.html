About EnMaaS

A common, governed front door for AI across Red Hat Engineering.

What is EnMaaS?

EnMaaS is Red Hat’s AI gateway for Engineering, built on Red Hat AI Technologies and forward-looking components expected to become part of the Red Hat AI Portfolio. It provides a common way to access supported model providers, including commercial and approved open-weight models, while simplifying model access and enabling a more consistent approach to governance, usage management, and future model enablement.

Why should I use EnMaaS?

EnMaaS gives you a single API key for approved AI models across multiple providers, including OpenAI and Anthropic, without separate credentials or onboarding for each platform. That includes models such as Opus 5.5 and approved open-weight options like GLM 5.3 and DeepSeek V4.1 Flash, available at no usage cost.

Access is managed through Atlas.

Use the Atlas onboarding flow to request, receive, and manage your EnMaaS key. The Atlas page requires the corporate VPN.

Model discovery and limits

The model catalog is useful, but it is not the complete source of truth for every credential type. Pin models in your client configuration when you need a model that is not listed.

Use the right authentication header

Authentication belongs to the gateway key, not to the selected model. For Anthropic Messages, a native EnMaaS key uses x-api-key together with the required anthropic-version HTTP header. OpenAI-compatible clients commonly use Authorization: Bearer; some gateway credentials also accept Bearer on Messages. Follow the credential instructions for your key and never put either credential in the JSON body.

curl "{{GATEWAY_URL}}/v1/models" -H "x-api-key: $ENMAAS_KEY"; curl "{{GATEWAY_URL}}/v1/models" -H "Authorization: Bearer $ENMAAS_KEY"

Catalog limitations

The /v1/models response can be credential-dependent and may omit hosted models even when inference works. Pi, OpenCode, and other clients should declare the exact hosted model ID locally when necessary:

rits/zai-org/glm-5-3
rits/deepseek-ai/DeepSeek-V4.1-Flash-1017

Hosted models support both gateway dialects where configured. DeepSeek was verified through Messages, Chat Completions, and Responses. DeepSeek has its own 1,000,000-token context window; do not copy GLM-only penalty or capability settings to DeepSeek.

!
Known hosted-model limits
rits/zai-org/glm-5-3 and rits/deepseek-ai/DeepSeek-V4.1-Flash-1017: 1,000,000-token context window and 65,536-token maximum output. Client settings must not declare a larger context window. Hosted models are served by vLLM: Responses API custom tools with a grammar format return HTTP 400, and built-in hosted tools such as web search are not executed. Other provider models have their own limits; use the provider’s documented model metadata when available.

Route supported models through one gateway.

Configure the EnMaaS base URL and key once, then select the exact model ID supported by the gateway. The gateway routes the request to the configured provider; it does not mean every upstream model is automatically available.

Keep the gateway settings; change the model

For Claude Code, Codex, OpenCode, and Pi, keep the EnMaaS URL and key unchanged when switching models. Change the client’s model entry to an exact gateway model ID. If a model is not shown by /v1/models, pin it locally only after confirming that EnMaaS supports it.

export ENMAAS_KEY='your-key'
# Keep this gateway base URL for every supported model
export ENMAAS_BASE_URL='{{GATEWAY_URL}}/v1'
# Set this per client to an exact supported model ID
MODEL_ID='exact-model-id'

Use the model’s API dialect

Use the endpoint and provider configuration that matches the model and client: Anthropic-compatible requests use /v1/messages; OpenAI Responses uses /v1/responses; OpenAI Chat Completions uses /v1/chat/completions. A model name alone does not change the request dialect.

# Anthropic Messages
-H "x-api-key: $ENMAAS_KEY" -H "anthropic-version: 2023-06-01"

# OpenAI-compatible APIs
-H "Authorization: Bearer $ENMAAS_KEY"
Tool-specific model settings: Claude Code changes the model through /model or modelPicker; Codex changes model in its EnMaaS profile; OpenCode changes its pinned provider model; Pi adds the model under the matching provider entry. GLM and DeepSeek are separate hosted models. Both declare a 1,000,000-token context window, but do not copy GLM-only penalty or capability settings to DeepSeek.

Use the tools you already know.

EnMaaS supports Claude Code, Codex, OpenCode, Pi, and Goose. More tools and recipes are coming soon. Keep your existing AI access available while EnMaaS is in beta.

Claude Code

Route Claude Code through EnMaaS, then use /model or model discovery to choose an available model.

1. Connect Claude Code to EnMaaS

Add or merge this into ~/.claude/settings.json.

{
  "env": {
    "ANTHROPIC_BASE_URL": "{{GATEWAY_URL}}",
    "ANTHROPIC_API_KEY": "your-enmaas-key",
    "CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY": "1"
  }
}
# Or use a shell session
export ANTHROPIC_BASE_URL="{{GATEWAY_URL}}"
    export ANTHROPIC_API_KEY="$ENMAAS_KEY"
    export CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1
    claude
!
Disable Claude Code’s direct Vertex mode.
Before starting Claude Code through EnMaaS, remove CLAUDE_CODE_USE_VERTEX, ANTHROPIC_VERTEX_PROJECT_ID, ANTHROPIC_VERTEX_REGION, and CLOUD_ML_REGION from your environment or ~/.claude/settings.json. If CLAUDE_CODE_USE_VERTEX=1 remains set, Claude Code bypasses the EnMaaS gateway and uses Vertex directly.
unset CLAUDE_CODE_USE_VERTEX ANTHROPIC_VERTEX_PROJECT_ID ANTHROPIC_VERTEX_REGION CLOUD_ML_REGION

Optional: use client-side auto-mode

If server-side auto-mode is unavailable or you prefer Claude Code to make the auto-mode decision locally, add this to the same env block in ~/.claude/settings.json.

"CLAUDE_CODE_AUTO_MODE_SERVER": "0"
Claude Code setting, not gateway routing.
This changes where Claude Code decides auto-mode; it does not change EnMaaS model routing, authentication, or authorization. This is a user-reported fallback: verify it with your installed Claude Code version and remove it or restore your settings backup if it does not behave as expected.

2. Add hosted models to the /model picker

Claude Code’s picker filters model IDs, so discovery alone may not show hosted models. EnMaaS exposes DeepSeek through /v1/models for Anthropic clients when requested with x-api-key and anthropic-version, but pinning the exact model locally keeps it visible in the picker. Add or merge these entries into ~/.claude/settings.json. This requires Claude Code 2.1.242 or newer. Claude Code will use the model’s native effort default; other harnesses should use their native defaults unless their provider configuration explicitly supports an effort setting.

ChatGPT desktop (macOS)

The desktop app is launched by macOS, so it only sees environment variables set at login. This adds the EnMaaS key at login, then gives the app a small catalog of three models.

Set up the desktop app

1. Make the key available at login

Replace YOUR_USERNAME in the plist with your account name. The key stays in the private env file; the LaunchAgent only exports it.

mkdir -p ~/.config/enmaas ~/.local/bin
printf 'ENMAAS_KEY="%s"\n' 'your-key' > ~/.config/enmaas/enmaas.env
chmod 600 ~/.config/enmaas/enmaas.env

cat > ~/.local/bin/set-codex-enmaas-env <<'EOF'
#!/bin/zsh
set -euo pipefail
set -a; source "$HOME/.config/enmaas/enmaas.env"; set +a
[[ -n "${ENMAAS_KEY:-}" ]] || { echo "ENMAAS_KEY is empty" >&2; exit 1; }
/bin/launchctl setenv ENMAAS_KEY "$ENMAAS_KEY"
EOF
chmod 700 ~/.local/bin/set-codex-enmaas-env

cat > ~/Library/LaunchAgents/com.enmaas.codex-env.plist <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>com.enmaas.codex-env</string>
  <key>ProgramArguments</key><array><string>/Users/YOUR_USERNAME/.local/bin/set-codex-enmaas-env</string></array>
  <key>RunAtLoad</key><true/>
</dict></plist>
EOF

launchctl bootout gui/$(id -u)/com.enmaas.codex-env 2>/dev/null || true
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.enmaas.codex-env.plist
[[ -n "$(launchctl getenv ENMAAS_KEY)" ]] && echo "key available"

When only hosted models are available

After your monthly budget is reached, the gateway can still allow GLM 5.3 while other models are denied. Claude Code auto-mode and Codex auto-review send their safety checks to a Sonnet or OpenAI review model by default, so point those at the hosted GLM 5.3 model too. These recipes use GLM 5.3 as the review model; DeepSeek V4.1 Flash is not covered here. Remove these settings once your other models are available again.

Claude Code auto-mode

The auto-mode classifier uses the Sonnet model tier, and subagents and background tasks use other tiers. Point every tier at the hosted model in the env block of ~/.claude/settings.json from the Claude Code setup.

"ANTHROPIC_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_OPUS_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_SONNET_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_HAIKU_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_FABLE_MODEL": "rits/zai-org/glm-5-3",
"CLAUDE_CODE_SUBAGENT_MODEL": "rits/zai-org/glm-5-3",
"CLAUDE_CODE_SUBAGENT_MODEL_FORCE": "1",
"CLAUDE_CODE_AUTO_MODE_SERVER": "0"
Known limitation: classifier timeouts with GLM.
GLM reasons by default when a request does not set thinking. The auto-mode classifier sends large prompts without a thinking setting, so GLM can spend long on reasoning before it answers. Claude Code 2.1.300 allows 60 seconds per attempt for the first classifier stage (up to 300 seconds with retries) and 120 seconds for the second stage, and these limits are not configurable. When a check exceeds them, Claude Code reports the classifier as temporarily unavailable (timed out) and denies that action. Whether Claude Code sends thinking as disabled, null, or not at all differs between versions, so the symptom can vary. Retry the action, or use a non-auto permission mode for long sessions. Fixes for this class of problem are in progress in vLLM itself (for example vllm#58613, vllm#58786, and vllm#61094), so these workarounds should become unnecessary once they ship.

Codex auto-review

With auto-review (approvals_reviewer = "auto_review"), Codex sends approval checks to the review model named in its model catalog, which is an OpenAI model by default. Generate a catalog entry that reviews with GLM 5.3 and only uses tools that hosted models accept, then add it to the enmaas profile from the Codex setup.

# Generate a GLM catalog entry from the catalog bundled with Codex
codex debug models --bundled | jq '[.models[] | select(.slug == "gpt-5.5")
  | .slug = "rits/zai-org/glm-5-3" | .display_name = "GLM 5.3 (EnMaaS)"
  | .auto_review_model_override = "rits/zai-org/glm-5-3"
  | .apply_patch_tool_type = null | .tool_mode = "direct"
  | .supports_search_tool = false | .input_modalities = ["text"]]
  | if length == 0 then error("bundled catalog has no gpt-5.5 entry")
    else {models: .} end' \
  > ~/.codex/enmaas-glm-models.json.tmp \
  && mv ~/.codex/enmaas-glm-models.json.tmp ~/.codex/enmaas-glm-models.json

# ~/.codex/enmaas.config.toml — add
model_catalog_json = "~/.codex/enmaas-glm-models.json"
web_search = "disabled"
Why these fields.
Hosted models are served by vLLM, which rejects Responses API custom tools that carry a grammar format (HTTP 400). The bundled Codex catalog entry for gpt-5.5 declares apply_patch as a freeform (grammar) tool, so this entry removes it and sets tool_mode to direct to avoid other grammar-based tools, and Codex edits files with shell commands instead. The vLLM fixes linked above are the intended long-term fix; the gateway does not rewrite client requests. Built-in web search is not executed for hosted models, and GLM 5.3 is text-only. Tested with Codex 0.162.1, and catalog generation re-checked with Codex 0.163.0. The command leaves an existing catalog untouched if the bundled catalog no longer has a gpt-5.5 entry; in that case select another bundled model.
