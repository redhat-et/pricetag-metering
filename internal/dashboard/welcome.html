About EnMaaS

A common, governed front door for AI across Red Hat Engineering.

What is EnMaaS?

EnMaaS is Red Hat’s AI gateway for Engineering, built on Red Hat AI Technologies and forward-looking components expected to become part of the Red Hat AI Portfolio. It provides a common way to access supported model providers, including commercial and approved open-weight models, while simplifying model access and enabling a more consistent approach to governance, usage management, and future model enablement.

Why should I use EnMaaS?

EnMaaS gives you a single API key for approved AI models across multiple providers, including OpenAI and Anthropic, without separate credentials or onboarding for each platform. That includes models such as Opus 5.5 and approved open-weight options like GLM 5.3, which is available at no usage cost.

Access is managed through Atlas.

Use the Atlas onboarding flow to request, receive, and manage your EnMaaS key. The Atlas page requires the corporate VPN.

Model discovery and limits

The model catalog is useful, but it is not the complete source of truth for every credential type. Pin models in your client configuration when you need a model that is not listed.

Use the right authentication header

Authentication belongs to the gateway key, not to the selected model. For Anthropic Messages, a native EnMaaS key uses x-api-key together with the required anthropic-version HTTP header. OpenAI-compatible clients commonly use Authorization: Bearer; some gateway credentials also accept Bearer on Messages. Follow the credential instructions for your key and never put either credential in the JSON body.

curl "{{GATEWAY_URL}}/v1/models" -H "x-api-key: $ENMAAS_KEY"; curl "{{GATEWAY_URL}}/v1/models" -H "Authorization: Bearer $ENMAAS_KEY"

Catalog limitations

The /v1/models response can be credential-dependent and may omit hosted models such as GLM 5.3 even when inference works. Pi, OpenCode, and other clients should declare the exact model ID locally when necessary:

rits/zai-org/glm-5-3

GLM 5.3 is text-only. Images in the request or conversation history return HTTP 400.

!
Known hosted-model limits
rits/zai-org/glm-5-3: 262,144-token context window and 65,536-token maximum output. Client settings must not declare a larger context window. Other provider models have their own limits; use the provider’s documented model metadata when available.

Route supported models through one gateway.

Configure the EnMaaS base URL and key once, then select the exact model ID supported by the gateway. The gateway routes the request to the configured provider; it does not mean every upstream model is automatically available.

Keep the gateway settings; change the model

For Claude Code, Codex, OpenCode, and Pi, keep the EnMaaS URL and key unchanged when switching models. Change the client’s model entry to an exact gateway model ID. If a model is not shown by /v1/models, pin it locally only after confirming that EnMaaS supports it.

export ENMAAS_KEY='your-key'
# Keep this gateway base URL for every supported model
export ENMAAS_BASE_URL='{{GATEWAY_URL}}/v1'
# Set this per client to an exact supported model ID
MODEL_ID='exact-model-id'

Use the model’s API dialect

Use the endpoint and provider configuration that matches the model and client: Anthropic-compatible requests use /v1/messages; OpenAI Responses uses /v1/responses; OpenAI Chat Completions uses /v1/chat/completions. A model name alone does not change the request dialect.

# Anthropic Messages
-H "x-api-key: $ENMAAS_KEY" -H "anthropic-version: 2023-06-01"

# OpenAI-compatible APIs
-H "Authorization: Bearer $ENMAAS_KEY"
Tool-specific model settings: Claude Code changes the model through /model or modelPicker; Codex changes model in its EnMaaS profile; OpenCode changes its pinned provider model; Pi adds the model under the matching provider entry. Do not copy a GLM-only context window or capability setting to another model.

Claude Code

Route Claude Code through EnMaaS, then use /model or model discovery to choose an available model.

1. Connect Claude Code to EnMaaS

Add or merge this into ~/.claude/settings.json.

{
  "env": {
    "ANTHROPIC_BASE_URL": "{{GATEWAY_URL}}",
    "ANTHROPIC_API_KEY": "your-enmaas-key",
    "CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY": "1"
  }
}
# Or use a shell session
export ANTHROPIC_BASE_URL="{{GATEWAY_URL}}"
export ANTHROPIC_API_KEY="$ENMAAS_KEY"
export CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1
claude

2. Add hosted models to the /model picker

Claude Code’s picker filters model IDs, so discovery alone may not show hosted models. Add or merge these entries into ~/.claude/settings.json. This requires Claude Code 2.1.242 or newer.

# ~/.claude/settings.json — add
{
  "modelPicker": {
    "options": [
      {
        "model": "rits/zai-org/glm-5-3",
        "label": "GLM 5.3",
        "description": "Hosted via EnMaaS"
      }
    ]
  },
  "modelSettings": {
    "rits/zai-org/glm-5-3": { "effortLevel": "medium" }
  }
}
!
Use the exact hosted model ID.
Run /models or /model after saving the settings. For GLM, use rits/zai-org/glm-5-3 exactly and keep effortLevel set to medium.
↩
Rollback if EnMaaS is unavailable
Exit Claude Code, restore your previous ~/.claude/settings.json backup, or remove the EnMaaS env block and relaunch. Keep the previous provider configuration unchanged so you can switch back immediately during this beta period.

Codex

Codex uses the OpenAI-compatible Responses API. Add EnMaaS as a provider and select it with a profile.

# ~/.codex/config.toml
[model_providers.enmaas]
name = "EnMaaS"
base_url = "{{GATEWAY_URL}}/v1"
env_key = "ENMAAS_KEY"
wire_api = "responses"

# ~/.codex/enmaas.config.toml
model = "rits/zai-org/glm-5-3"
model_provider = "enmaas"

# Use the EnMaaS profile
export ENMAAS_KEY="your-enmaas-key"
codex --profile enmaas

Keep the model provider set to enmaas for EnMaaS requests. Change the model line only to an exact model ID supported by the gateway; the catalog may omit hosted models, so keep the pinned model entry explicit.

↩
Rollback if EnMaaS is unavailable
Stop using the enmaas profile and return to your existing Codex profile, for example codex --profile default. Do not delete your old config; keeping both profiles makes rollback immediate while the service is being scaled and stabilized.

Save your current configuration first so you can switch back easily.

OpenCode

Use an isolated OpenCode configuration so your normal sessions remain untouched. The /models command lets you inspect the available EnMaaS models.

# ~/.config/opencode-enmaas/opencode/opencode.jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "model": "openai/rits/zai-org/glm-5-3",
  "providers": {
    "openai": {
      "settings": { "baseURL": "{{GATEWAY_URL}}/v1" },
      "env": ["ENMAAS_KEY"]
    },
    "anthropic": {
      "settings": { "baseURL": "{{GATEWAY_URL}}/v1" },
      "env": ["ENMAAS_KEY"]
    }
  }
}
# Isolate this test configuration
export ENMAAS_KEY="your-enmaas-key"
export XDG_CONFIG_HOME="$HOME/.config/opencode-enmaas"
export XDG_DATA_HOME="$HOME/.local/share/opencode-enmaas"
opencode --standalone

# Inside OpenCode
/models

Use the provider matching the model's API dialect: Anthropic-compatible models use /v1/messages; OpenAI-compatible models use /v1/responses or /v1/chat/completions. The catalog is advisory and can omit models for some credential types; the local provider model entries and the pinned model are the source of truth for what this client can select.

OpenCode does not need a separate model-picker block. Its /models command may read the gateway catalog, but the catalog is not authoritative for every credential type. Pin the default model locally and use an exact supported model ID even when it is absent from the catalog.

↩
Rollback if EnMaaS is unavailable
Close the standalone EnMaaS process and run your normal opencode command without the EnMaaS environment variables. Your normal XDG_CONFIG_HOME and XDG_DATA_HOME remain separate, so existing sessions and providers are preserved.

Pi

Use the provider and API dialect required by the model. The example below configures GLM 5.3; add other supported models to the same provider or a separate provider entry with their exact model ID and documented limits.

{
  "providers": {
    "enmaas-glm-5-3": {
      "baseUrl": "{{GATEWAY_URL}}/v1",
      "api": "openai-completions",
      "models": [{
        "id": "rits/zai-org/glm-5-3",
        "name": "GLM 5.3 (EnMaaS)",
        "reasoning": true,
        "input": ["text"],
        "contextWindow": 262144,
        "maxTokens": 65536,
        "cost": {"input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0},
        "compat": {"supportsDeveloperRole": false}
      }]
    }
  }
}
# ~/.pi/agent/auth.json — chmod 0600
{
  "enmaas-glm-5-3": {
    "type": "api_key",
    "key": "your-enmaas-key"
  }
}

# Smoke test
pi --provider enmaas-glm-5-3 --model "rits/zai-org/glm-5-3" -p "Reply with exactly: OK"
!
Pin the model directly.
The /v1/models response is not authoritative for every credential type, so GLM may not appear in Pi’s model search even when inference works. The pinned entry above keeps it available in /model. Use a repetition/frequency penalty of 1.0 (off) if your Pi configuration exposes it; penalties can make GLM drift into Chinese.
