About EnMaaS

A common, governed front door for AI across Red Hat Engineering.

What is EnMaaS?

EnMaaS is Red Hat’s AI gateway for Engineering, built on Red Hat AI Technologies and forward-looking components expected to become part of the Red Hat AI Portfolio. It provides a common way to access supported model providers, including commercial and approved open-weight models, while simplifying model access and enabling a more consistent approach to governance, usage management, and future model enablement.

Why should I use EnMaaS?

EnMaaS gives you a single API key for approved AI models across multiple providers, including OpenAI and Anthropic, without separate credentials or onboarding for each platform. That includes models such as Opus 5.5 and approved open-weight options like GLM 5.3 and DeepSeek V4.1 Flash, available at no usage cost.

Access is managed through Atlas.

Use the Atlas onboarding flow to request, receive, and manage your EnMaaS key. The Atlas page requires the corporate VPN.

Model discovery and limits

The model catalog is useful, but it is not the complete source of truth for every credential type. Pin models in your client configuration when you need a model that is not listed.

Use the right authentication header

Authentication belongs to the gateway key, not to the selected model. For Anthropic Messages, a native EnMaaS key uses x-api-key together with the required anthropic-version HTTP header. OpenAI-compatible clients use Authorization: Bearer. On /v1/messages, use x-api-key; Authorization: Bearer is not accepted there when anthropic-version is present. Never put either credential in the JSON body.

curl "https://api.enmaas.devshift.net/v1/models" -H "x-api-key: $ENMAAS_KEY"; curl "https://api.enmaas.devshift.net/v1/models" -H "Authorization: Bearer $ENMAAS_KEY"

Catalog limitations

The /v1/models response can be credential-dependent and may omit hosted models even when inference works. Pi, OpenCode, and other clients should declare the exact hosted model ID locally when necessary:

rits/zai-org/glm-5-3
rits/deepseek-ai/DeepSeek-V4.1-Flash-1017

Hosted models support both gateway dialects where configured. DeepSeek was verified through Messages, Chat Completions, and Responses. Do not copy GLM-specific context-window, penalty, or capability settings to DeepSeek.

!
Known hosted-model limits
rits/zai-org/glm-5-3: 1,000,000-token context window and 65,536-token maximum output. Client settings must not declare a larger context window. Hosted models are served by vLLM: Responses API custom tools with a grammar format return HTTP 400, and built-in hosted tools such as web search are not executed. GLM 5.3 is text-only, so images in the request or conversation history return HTTP 400. GLM 5.3 also does not support server-side tool execution; tool-injection requests can return HTTP 400, and Claude Code works around this with web_fetch. GLM streaming can also emit finish_reason before all content and reasoning deltas finish; strict SSE clients may truncate the turn. Some older Claude IDs (for example claude-sonnet-4-5, claude-opus-4-5, and claude-opus-4-7) may return 404; use the current IDs returned by /v1/models. Other provider models have their own limits; use the provider’s documented model metadata when available.
!
Request size limit: 10 MiB
The gateway currently rejects request bodies larger than 10 MiB with HTTP 413. Long sessions, especially those carrying encrypted reasoning state, can reach this limit. Start a new session, switch models to drop provider-specific reasoning metadata, or compact the conversation when the client supports it. The team is working to raise the limit to 32 MiB.

Route supported models through one gateway.

Configure the EnMaaS base URL and key once, then select the exact model ID supported by the gateway. The gateway routes the request to the configured provider; it does not mean every upstream model is automatically available.

Keep the gateway settings; change the model

For Claude Code, Codex, OpenCode, and Pi, keep the EnMaaS URL and key unchanged when switching models. Change the client’s model entry to an exact gateway model ID. If a model is not shown by /v1/models, pin it locally only after confirming that EnMaaS supports it.

export ENMAAS_KEY='your-key'
# Keep this gateway base URL for every supported model
export ENMAAS_BASE_URL='https://api.enmaas.devshift.net/v1'
# Set this per client to an exact supported model ID
MODEL_ID='exact-model-id'

Use the model’s API dialect

Use the endpoint and provider configuration that matches the model and client: Anthropic-compatible requests use /v1/messages; OpenAI Responses uses /v1/responses; OpenAI Chat Completions uses /v1/chat/completions. A model name alone does not change the request dialect.

# Anthropic Messages
-H "x-api-key: $ENMAAS_KEY" -H "anthropic-version: 2023-06-01"

# OpenAI-compatible APIs
-H "Authorization: Bearer $ENMAAS_KEY"
Tool-specific model settings: Claude Code changes the model through /model or modelPicker; Codex changes model in its EnMaaS profile; OpenCode changes its pinned provider model; Pi adds the model under the matching provider entry. GLM and DeepSeek are separate hosted models: do not copy GLM-only context-window, penalty, or capability settings to DeepSeek.

Claude Code

Route Claude Code through EnMaaS, then use /model or model discovery to choose an available model.

1. Connect Claude Code to EnMaaS

Add or merge this into ~/.claude/settings.json. You do not need Vertex to use Claude Code with EnMaaS.

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.enmaas.devshift.net",
    "ANTHROPIC_API_KEY": "your-enmaas-key",
    "CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY": "1",
    "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1"
  }
}
# Or use a shell session
export ANTHROPIC_BASE_URL="https://api.enmaas.devshift.net"
export ANTHROPIC_API_KEY="$ENMAAS_KEY"
export CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY=1
export CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1
claude

Privacy: CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1 disables Claude Code’s Sentry reporting, feature flags, update checks, and usage telemetry. It does not disable side-channel model requests such as safety checks or session-title generation.

!
Answer yes to the key prompt.
The first time Claude Code starts with the EnMaaS key, it asks whether to use it. Answer yes; dismissing the prompt records the key as rejected. If you later see Not logged in · Please run /login, quit Claude Code first (it rewrites ~/.claude.json on close), remove customApiKeyResponses from ~/.claude.json, restart Claude Code, and answer yes. A rejected key looks like no key at all.
!
Disable Claude Code’s direct Vertex mode.
Before starting Claude Code through EnMaaS, remove every occurrence of CLAUDE_CODE_USE_VERTEX, ANTHROPIC_VERTEX_PROJECT_ID, ANTHROPIC_VERTEX_REGION, CLOUD_ML_REGION, and any ANTHROPIC_DEFAULT_* variable that still points at a Vertex or Google model ID. They can persist in shell startup files, the env block in ~/.claude/settings.json, and the systemd user environment. A variable inherited from the shell never appears in settings.json. If CLAUDE_CODE_USE_VERTEX=1 remains set, Claude Code bypasses EnMaaS and uses Vertex directly. The ANTHROPIC_DEFAULT_* values use Google’s name@date format, which EnMaaS does not recognize, so leaving them produces model-not-found errors.
# Find every copy first
cd ~
grep -IslE "VERTEX|CLOUD_ML|ANTHROPIC_DEF" .bashrc .bash_profile .profile
grep -IslE "VERTEX|CLOUD_ML|ANTHROPIC_DEF" .zshrc .zprofile .env
grep -IslE "VERTEX|CLOUD_ML|ANTHROPIC_DEF" .claude/settings*.json
grep -rIslE "ANTHROPIC_VERTEX|USE_VERTEX" .config --include="*.sh"
systemctl --user show-environment | grep -iE "VERTEX|CLOUD_ML|ANTHROPIC_DEF"

# Remove from the current shell, shell files, and systemd user environment
unset CLAUDE_CODE_USE_VERTEX ANTHROPIC_VERTEX_PROJECT_ID ANTHROPIC_VERTEX_REGION CLOUD_ML_REGION
unset ANTHROPIC_DEFAULT_OPUS_MODEL ANTHROPIC_DEFAULT_SONNET_MODEL ANTHROPIC_DEFAULT_HAIKU_MODEL ANTHROPIC_DEFAULT_FABLE_MODEL
systemctl --user unset-environment CLAUDE_CODE_USE_VERTEX ANTHROPIC_VERTEX_PROJECT_ID ANTHROPIC_VERTEX_REGION CLOUD_ML_REGION
systemctl --user unset-environment ANTHROPIC_DEFAULT_OPUS_MODEL ANTHROPIC_DEFAULT_SONNET_MODEL ANTHROPIC_DEFAULT_HAIKU_MODEL ANTHROPIC_DEFAULT_FABLE_MODEL

# Close and reopen your terminal, then confirm
test -z "$CLAUDE_CODE_USE_VERTEX" && echo "CLEAN" || echo "STILL SET"

Need Vertex and EnMaaS side by side? Use a separate CLAUDE_CONFIG_DIR for the EnMaaS profile and keep your existing Vertex environment in your normal shell. On GNOME, opening a new terminal can reuse the existing terminal server, so log out and back in if the variable persists.

Optional: use client-side auto-mode

If server-side auto-mode is unavailable or you prefer Claude Code to make the auto-mode decision locally, add this to the same env block in ~/.claude/settings.json.

"CLAUDE_CODE_AUTO_MODE_SERVER": "0"
Claude Code setting, not gateway routing.
This changes where Claude Code decides auto-mode; it does not change EnMaaS model routing, authentication, or authorization. This is a user-reported fallback: verify it with your installed Claude Code version and remove it or restore your settings backup if it does not behave as expected.

Claude Code’s picker filters model IDs, so discovery alone may not show hosted models. EnMaaS exposes DeepSeek through /v1/models for Anthropic clients when requested with x-api-key and anthropic-version, but pinning the exact model locally keeps it visible in the picker. Add or merge these entries into ~/.claude/settings.json. This requires Claude Code 2.1.242 or newer. The top-level model key is required; modelPicker alone is not sufficient. Claude Code will use the model’s native effort default; other harnesses should use their native defaults unless their provider configuration explicitly supports an effort setting.

Codex

Codex uses the OpenAI-compatible Responses API. DeepSeek Responses was verified with EnMaaS. Add EnMaaS as a provider and select it with a profile. To use DeepSeek, set the profile model to rits/deepseek-ai/DeepSeek-V4.1-Flash-1017 after confirming the model is available.

# ~/.codex/enmaas.config.toml — keep the profile self-contained
model = "rits/zai-org/glm-5-3"
# Or use: rits/deepseek-ai/DeepSeek-V4.1-Flash-1017
model_provider = "enmaas"

[model_providers.enmaas]
name = "EnMaaS"
base_url = "https://api.enmaas.devshift.net/v1"
env_key = "ENMAAS_KEY"
wire_api = "responses"

# Use the EnMaaS profile
export ENMAAS_KEY="your-enmaas-key"
codex --profile enmaas

Codex profiles are self-contained: keep the [model_providers.enmaas] block in the profile file itself. If the provider is defined only in ~/.codex/config.toml, the profile may fall back to OpenAI and return 401 Unauthorized. Change the model line only to an exact model ID supported by the gateway; the catalog may omit hosted models, so keep the pinned model entry explicit.

OpenAI/GPT models: when a profile targets an OpenAI/GPT model through EnMaaS, add service_tier = "default" to the top-level ~/.codex/config.toml, not to the profile file. It is not required for GLM or DeepSeek.

!
Known Codex and hosted-model limits.
GLM 5.3 through the Responses API can return HTTP 400 for unsupported item types such as additional_tools, compaction, or image content in history. Codex may also drop the configured GLM context window to about 258K after the first prompt. Keep sessions short, avoid image or tool-injected content, or use DeepSeek for Responses; the CLI has no client-side context-window override today.

The desktop app is launched by macOS, so it only sees environment variables set at login. This adds the EnMaaS key at login, then gives the app a small catalog of three models.

1. Make the key available at login

Replace YOUR_USERNAME in the plist with your account name. The key stays in the private env file; the LaunchAgent only exports it.

mkdir -p ~/.config/enmaas ~/.local/bin
printf 'ENMAAS_KEY="%s"
' 'your-key' > ~/.config/enmaas/enmaas.env
chmod 600 ~/.config/enmaas/enmaas.env

cat > ~/.local/bin/set-codex-enmaas-env <<'EOF'
#!/bin/zsh
set -euo pipefail
set -a; source "$HOME/.config/enmaas/enmaas.env"; set +a
[[ -n "${ENMAAS_KEY:-}" ]] || { echo "ENMAAS_KEY is empty" >&2; exit 1; }
/bin/launchctl setenv ENMAAS_KEY "$ENMAAS_KEY"
EOF
chmod 700 ~/.local/bin/set-codex-enmaas-env

cat > ~/Library/LaunchAgents/com.enmaas.codex-env.plist <<'EOF'
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>com.enmaas.codex-env</string>
  <key>ProgramArguments</key><array><string>/Users/YOUR_USERNAME/.local/bin/set-codex-enmaas-env</string></array>
  <key>RunAtLoad</key><true/>
</dict></plist>
EOF

launchctl bootout gui/$(id -u)/com.enmaas.codex-env 2>/dev/null || true
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.enmaas.codex-env.plist
[[ -n "$(launchctl getenv ENMAAS_KEY)" ]] && echo "key available"

OpenCode v2 configuration

1. OpenCode v2 — ~/.config/opencode-enmaas/opencode/opencode.json

v2 uses the providers key (plural) and the bundled @opencode/ai/providers/openai-compatible runtime, so no npm packages are needed. Each provider reads its credential from ENMAAS_KEY via the env list, and "update": "disable" turns off update checks. The example keeps hosted models under the custom enmaas provider; if you use the built-in openai provider instead, add the hosted model IDs under its models block. The --standalone flag is v2-only; do not use it with v1.

{
  "$schema": "https://opencode.ai/config.json",
  "model": "enmaas/rits/zai-org/glm-5-3",
  // To test DeepSeek, use: enmaas/rits/deepseek-ai/DeepSeek-V4.1-Flash-1017
  "update": "disable",
  "providers": {
    "enmaas": {
      "name": "EnMaaS",
      "env": ["ENMAAS_KEY"],
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://api.enmaas.devshift.net/v1"
      },
      "models": {
         "rits/zai-org/glm-5-3": {
           "name": "GLM 5.3",
           "limit": { "context": 1048576, "output": 65536 }
         },
         "rits/deepseek-ai/DeepSeek-V4.1-Flash-1017": {
           "name": "DeepSeek V4.1 Flash"
         }
      }
    },
    "openai": {
      "env": ["ENMAAS_KEY"],
      "settings": { "baseURL": "https://api.enmaas.devshift.net/v1" }
    },
    "anthropic": {
      "env": ["ENMAAS_KEY"],
      "settings": { "baseURL": "https://api.enmaas.devshift.net/v1" }
    }
  }
}

1. OpenCode v1 — ~/.config/opencode-enmaas/opencode/opencode.json

v1 uses the provider key (singular) and references the @ai-sdk/openai-compatible npm runtime, which must be installed next to the config for the custom enmaas provider to load. The credential is substituted inline from ENMAAS_KEY via {env:ENMAAS_KEY}.

{
  "$schema": "https://opencode.ai/config.json",
  "model": "enmaas/rits/zai-org/glm-5-3",
  // To test DeepSeek (including image input), use: enmaas/rits/deepseek-ai/DeepSeek-V4.1-Flash-1017
  "provider": {
    "enmaas": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "EnMaaS",
      "options": {
        "baseURL": "https://api.enmaas.devshift.net/v1",
        "apiKey": "{env:ENMAAS_KEY}"
      },
      "models": {
         "rits/zai-org/glm-5-3": {
           "name": "GLM 5.3",
           "limit": {
             "context": 1048576,
             "output": 65536
           }
         },
         "rits/deepseek-ai/DeepSeek-V4.1-Flash-1017": {
           "name": "DeepSeek V4.1 Flash",
           "limit": {
             "context": 1048576,
             "output": 65536
           },
           "modalities": {
             "input": ["text", "image"],
             "output": ["text"]
           }
         }
      }
    },
    "openai": {
      "options": {
        "baseURL": "https://api.enmaas.devshift.net/v1",
        "apiKey": "{env:ENMAAS_KEY}"
      }
    },
    "anthropic": {
      "options": {
        "baseURL": "https://api.enmaas.devshift.net/v1",
        "apiKey": "{env:ENMAAS_KEY}"
      }
    }
  }
}
DeepSeek image input.
OpenCode v1 sends images only when the selected model declares image input. The modalities block in this example enables vision for DeepSeek V4.1 Flash; GLM 5.3 is text-only, so do not add it there. Switch the pinned model to the DeepSeek ID to use vision.

2. Run v1 against EnMaaS

Install the provider runtime next to the config once, then isolate the configuration and start the v1 TUI. Use /models inside OpenCode to inspect the gateway catalog.

# One-time: install the provider runtime next to the config
npm install --prefix "$HOME/.config/opencode-enmaas/opencode" @ai-sdk/openai-compatible

# Isolate this test configuration
export ENMAAS_KEY="your-enmaas-key"
export XDG_CONFIG_HOME="$HOME/.config/opencode-enmaas"
export XDG_DATA_HOME="$HOME/.local/share/opencode-enmaas"
opencode

# Inside OpenCode
/models

Use the provider matching the model's API dialect: Anthropic-compatible models use /v1/messages; OpenAI-compatible models use /v1/responses or /v1/chat/completions. The catalog is advisory and can omit models for some credential types; the local provider model entries and the pinned model are the source of truth for what this client can select.

OpenCode does not need a separate model-picker block. For DeepSeek, add rits/deepseek-ai/DeepSeek-V4.1-Flash-1017 to the pinned OpenAI-compatible provider model list. Its /models command may read the gateway catalog, but the catalog is not authoritative for every credential type. Pin the default model locally and use an exact supported model ID even when it is absent from the catalog.

↩
Rollback if EnMaaS is unavailable
Close the standalone EnMaaS process and run your normal opencode command without the EnMaaS environment variables. Your normal XDG_CONFIG_HOME and XDG_DATA_HOME remain separate, so existing sessions and providers are preserved.

Pi

Route all of Pi’s model families through EnMaaS with one key: OpenAI, Anthropic, and the hosted GLM and DeepSeek models. Merge the entries below into the providers object of your existing ~/.pi/agent/models.json.

1. Route Pi’s providers through EnMaaS

The openai and anthropic entries override Pi’s built-in providers without a models list, so their full catalogues (gpt-*, claude-*) stay available while routing through the gateway. The base URLs match Pi’s built-in defaults: openai keeps the /v1 suffix, anthropic stays bare because Pi appends /v1/messages itself. The enmaas-glm-5-3 entry pins both hosted OpenAI-compatible models: GLM 5.3 and DeepSeek V4.1 Flash.

{
  "providers": {
    "openai": {
      "baseUrl": "https://api.enmaas.devshift.net/v1"
    },
    "anthropic": {
      "baseUrl": "https://api.enmaas.devshift.net",
      "compat": {"supportsMidConvoEffort": false},
      "modelOverrides": {
        "claude-opus-5-5": {"compat": {"supportsStrictTools": false}},
        "claude-haiku-5-5": {"compat": {"supportsStrictTools": false}}
      }
    },
    "enmaas-glm-5-3": {
      "baseUrl": "https://api.enmaas.devshift.net/v1",
      "api": "openai-completions",
      "models": [{
        "id": "rits/zai-org/glm-5-3",
        "name": "GLM 5.3 (EnMaaS)",
        "reasoning": true,
        "input": ["text"],
         "contextWindow": 1048576,
        "maxTokens": 65536,
        "cost": {"input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0},
        "compat": {"supportsDeveloperRole": false},
         "samplingParams": {"frequency_penalty": 0, "presence_penalty": 0}
       },
       {
         "id": "rits/deepseek-ai/DeepSeek-V4.1-Flash-1017",
         "name": "DeepSeek V4.1 Flash (EnMaaS)",
         "input": ["text"],
         "cost": {"input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0},
         "compat": {"supportsDeveloperRole": false}
       }]
    }
  }
}

Claude 5.x models: the provider-level supportsMidConvoEffort: false prevents output_config validation errors. Opus 5.5 and Haiku 5.5 also need supportsStrictTools: false until the GCP organization policy allows structured outputs for those models. Remove the overrides once the policy is updated.

2. Store the key and smoke test

Add an entry for each provider to ~/.pi/agent/auth.json so every model family authenticates with the same EnMaaS key. Keep the file private.

# ~/.pi/agent/auth.json — chmod 0600
{
  "openai": {
    "type": "api_key",
    "key": "your-enmaas-key"
  },
  "anthropic": {
    "type": "api_key",
    "key": "your-enmaas-key"
  },
  "enmaas-glm-5-3": {
    "type": "api_key",
    "key": "your-enmaas-key"
  }
}

# Smoke test
pi --provider enmaas-glm-5-3 --model "rits/zai-org/glm-5-3" -p "Reply with exactly: OK"
# DeepSeek uses the same OpenAI-compatible pinned provider
pi --provider enmaas-glm-5-3 --model "rits/deepseek-ai/DeepSeek-V4.1-Flash-1017" -p "Reply with exactly: OK"

Frontier models appear in /model with their usual Pi catalogue entries; select any of them and the request routes through EnMaaS. Use the provider matching the model family — openai/* and enmaas-glm-5-3/* speak OpenAI dialects, anthropic/* uses Messages.

!
Pin hosted models directly.
The /v1/models response is not authoritative for every credential type, so GLM or DeepSeek may not appear in Pi’s model search even when inference works. The pinned entries above keep them available in /model. Keep the GLM samplingParams penalties at 0; those penalties can make GLM drift into Chinese.
↩
Rollback if EnMaaS is unavailable
Restore your backed-up ~/.pi/agent/models.json, or remove the EnMaaS entries so openai and anthropic return to their built-in endpoints, and relaunch Pi. Keeping the backup makes rollback immediate while the service is being scaled and stabilized.

2. Configure the API key in Goose

Run Goose, select Configure Providers, search for enmaas, and configure the API key when prompted. Goose uses the CUSTOM_ENMAAS_API_KEY variable declared in the provider file.

goose configure
The provider file contains no secret.
Keep the API key private and use the exact model ID rits/zai-org/glm-5-3 or rits/deepseek-ai/DeepSeek-V4.1-Flash-1017.

When only hosted models are available

After your monthly budget is reached, the gateway can still allow GLM 5.3 while other models are denied. Claude Code auto-mode and Codex auto-review send their safety checks to a Sonnet or OpenAI review model by default, so point those at the hosted GLM 5.3 model too. These recipes use GLM 5.3 as the review model; DeepSeek V4.1 Flash is not covered here. Remove these settings once your other models are available again.

Claude Code auto-mode

The auto-mode classifier uses the Sonnet model tier, and subagents and background tasks use other tiers. Point every tier at the hosted model in the env block of ~/.claude/settings.json from the Claude Code setup.

"ANTHROPIC_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_OPUS_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_SONNET_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_HAIKU_MODEL": "rits/zai-org/glm-5-3",
"ANTHROPIC_DEFAULT_FABLE_MODEL": "rits/zai-org/glm-5-3",
"CLAUDE_CODE_SUBAGENT_MODEL": "rits/zai-org/glm-5-3",
"CLAUDE_CODE_SUBAGENT_MODEL_FORCE": "1",
"CLAUDE_CODE_AUTO_MODE_SERVER": "0"
Known limitation: classifier timeouts with GLM.
GLM reasons by default when a request does not set thinking. The auto-mode classifier sends large prompts without a thinking setting, so GLM can spend long on reasoning before it answers. Claude Code 2.1.300 allows 60 seconds per attempt for the first classifier stage (up to 300 seconds with retries) and 120 seconds for the second stage, and these limits are not configurable. When a check exceeds them, Claude Code reports the classifier as temporarily unavailable (timed out) and denies that action. Whether Claude Code sends thinking as disabled, null, or not at all differs between versions, so the symptom can vary. Retry the action, or use a non-auto permission mode for long sessions. Fixes for this class of problem are in progress in vLLM itself (for example vllm#58613, vllm#58786, and vllm#61094), so these workarounds should become unnecessary once they ship.

Codex auto-review

With auto-review (approvals_reviewer = "auto_review"), Codex sends approval checks to the review model named in its model catalog, which is an OpenAI model by default. Generate a catalog entry that reviews with GLM 5.3 and only uses tools that hosted models accept, then add it to the enmaas profile from the Codex setup.

# Generate a GLM catalog entry from the catalog bundled with Codex
codex debug models --bundled | jq '[.models[] | select(.slug == "gpt-5.5")
  | .slug = "rits/zai-org/glm-5-3" | .display_name = "GLM 5.3 (EnMaaS)"
  | .auto_review_model_override = "rits/zai-org/glm-5-3"
  | .apply_patch_tool_type = null | .tool_mode = "direct"
  | .supports_search_tool = false | .input_modalities = ["text"]]
  | if length == 0 then error("bundled catalog has no gpt-5.5 entry")
    else {models: .} end' \
  > ~/.codex/enmaas-glm-models.json.tmp \
  && mv ~/.codex/enmaas-glm-models.json.tmp ~/.codex/enmaas-glm-models.json

# ~/.codex/enmaas.config.toml — add
model_catalog_json = "~/.codex/enmaas-glm-models.json"
web_search = "disabled"
Why these fields.
Hosted models are served by vLLM, which rejects Responses API custom tools that carry a grammar format (HTTP 400). The bundled Codex catalog entry for gpt-5.5 declares apply_patch as a freeform (grammar) tool, so this entry removes it and sets tool_mode to direct to avoid other grammar-based tools, and Codex edits files with shell commands instead. The vLLM fixes linked above are the intended long-term fix; the gateway does not rewrite client requests. Built-in web search is not executed for hosted models, and GLM 5.3 is text-only. Tested with Codex 0.162.1, and catalog generation re-checked with Codex 0.163.0. The command leaves an existing catalog untouched if the bundled catalog no longer has a gpt-5.5 entry; in that case select another bundled model.

Know what to expect.

EnMaaS is being scaled out and tuned. We want you to know how to keep working while it evolves.

!
Availability and model stability
Models, capacity, and routing are still being expanded. Short service interruptions or model availability changes may occur during updates and scaling.
↩
Keep a fallback ready
For important work, retain your previous provider configuration and workflow. If EnMaaS is temporarily unavailable, switch back to that workflow and retry later.
↩
Clean up stale provider settings
Before you rely on EnMaaS, remove old direct-provider settings from shell startup files, the systemd user environment, and client config files. Keep a backup so you can switch back. The Claude Code section above includes the full Vertex cleanup commands.
